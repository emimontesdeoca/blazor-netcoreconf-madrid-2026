TIEMPO: 0:45 – 2:00 Un componente puede ser un botón, una ficha de producto o una tabla. Podemos combinar varios componentes para construir una página. En el ejemplo, al pulsar el botón se ejecuta un método de C# y cambia el contador. Para que responda al clic necesita un modo interactivo, como el de nuestra demo. El navegador sigue mostrando HTML y CSS. Blazor utiliza JavaScript internamente y también permite llamar a bibliotecas de JavaScript. Con esta idea de componente basta para seguir la charla. Referencia: https://learn.microsoft.com/aspnet/core/blazor/

TIEMPO: 2:00 – 3:00 Al renderizar, Blazor ejecuta el marcado del componente, compara el resultado con el anterior y aplica al DOM solo los cambios necesarios. El DOM es la estructura de la página que mantiene el navegador. Renderizar no significa generar de nuevo todo el HTML de la pantalla. La demo usa Interactive Server en toda la aplicación. El prerender está desactivado para medir una sola ejecución interactiva. Las técnicas también sirven para WebAssembly, pero el coste del renderizado se produce en el navegador, no en el servidor. Static SSR también puede repetir consultas o generar demasiado HTML, pero no tiene estos eventos interactivos. Si preguntan por Auto: puede usar Server al principio y WebAssembly en visitas posteriores. No cambia el modo de un componente que ya está abierto.

TIEMPO: 3:00 – 4:00 Enseñar el menú, el selector Lento/Rápido y el panel de diagnóstico. Explicar que cada página muestra un problema y dos implementaciones. Los datos son ficticios y la API está simulada dentro del servidor. Las llamadas que cuenta el panel no son peticiones HTTP del navegador. El panel cuenta renderizados y llamadas. No mide imágenes por segundo. En cada demo haremos la misma acción en ambos modos y compararemos los números. Para la versión de 30 minutos, seguir los tiempos de PREPARACION.md.

TIEMPO: 4:00 – 5:00 Mostrar el flujo: el reloj actualiza el padre y este vuelve a pasar el mismo Pedido a sus 200 hijos. Pedido es el modelo mutable de una fila, no el componente. Pasar objetos no es un error por sí mismo. Aquí el problema es repetir el renderizado de 200 componentes cuyos datos no han cambiado. Si todos los parámetros son tipos inmutables conocidos y siguen teniendo los mismos valores, Blazor puede omitir su actualización. Un record definido por nosotros no se considera automáticamente uno de esos tipos. Los eventos y los cambios de estado también pueden solicitar renderizados. Un manejador asíncrono que queda pendiente suele solicitar uno al devolver el control y otro al terminar. Eso no garantiza exactamente dos renderizados. Referencia: https://learn.microsoft.com/aspnet/core/blazor/components/rendering

TIEMPO: 5:00 – 8:00 Volver al mismo hijo, ahora optimizado; el padre y su bucle no cambian. Ruta: /renderizados. Aumentar el zoom para que se lean el panel y los contadores. Validación del 21/10: 400 renderizados en dos actualizaciones del reloj; 0 en Rápido después de reiniciar. Al marcar el pedido, el contador de la primera fila pasa de 1 a 2 y los de las otras 199 siguen en 1. Al cambiar de implementación, las 200 filas tienen que renderizarse una vez. Esperar a que aparezcan antes de reiniciar el panel. El panel cuenta los componentes que hemos instrumentado, no todos los de la app, y se actualiza como máximo cuatro veces por segundo. Si falla la demo, explicar el resultado esperado con este código.

TIEMPO: 8:00 – 8:40 Esto no impide que el padre pase parámetros ni evita todo el ciclo de vida. Evita reconstruir el árbol de renderizado de una fila sin cambios. Si no puedes garantizar que Version cubra todos los campos visibles, compara esos campos o pasa parámetros primitivos.

TIEMPO: 9:00 – 10:00 Seguir la conexión del input con `@oninput="Buscar"`: cada tecla llama al método. Hay dos problemas: se hacen llamadas que no necesitamos y pueden mostrarse resultados que ya no corresponden al texto del buscador. La API no consulta si el texto está vacío. Por eso, vaciar el campo al iniciar la simulación no añade una novena llamada. Cada búsqueda tarda 250 ms, salvo "mart", que añade 800 ms de retraso. Así podemos reproducir una respuesta desactualizada sin depender del azar. La latencia es artificial; no estamos midiendo una API externa.

TIEMPO: 10:00 – 14:00 Mostrar el código ANTES y avanzar para transformar el bloque en DESPUÉS. Ruta: /eventos. Pulsar el botón «Escribir martinez» en ambos modos. Antes de comparar, esperar a que el contador de llamadas en curso llegue a 0. Cambiar a Rápido, reiniciar y repetir. Validación del 21/10: 8 llamadas y resultados de "mart" en Lento; 1 llamada y resultados de "martinez" en Rápido. El botón simula una tecla cada 90 ms. Para mostrar la cancelación, escribir "mart", esperar a que empiece la llamada y escribir "martinez". El panel cuenta cancelaciones de llamadas iniciadas, no las esperas de Task.Delay que se cancelan antes de consultar. Mantener visible la pestaña durante la demo. El navegador puede ralentizar los temporizadores de las pestañas que están en segundo plano.

TIEMPO: 14:00 – 14:45 La cancelación es cooperativa: hay que pasar el token a HttpClient o EF Core cuando lo admitan. Comprobarlo antes de asignar el resultado evita mostrar una respuesta desactualizada si la operación no se canceló a tiempo. Si la API no acepta un token, se puede descartar la respuesta con un identificador de solicitud. Eso evita mostrarla, pero no reduce el trabajo de la API.

TIEMPO: 15:00 – 16:00 Las 30.000 celdas no son todos los nodos del DOM: también hay filas y otros elementos. El foreach genera todas las filas y vuelve a recorrerlas en cada renderizado. En Interactive Server, los cambios necesarios del DOM viajan por SignalR. Esto no significa que el primer renderizado siempre llegue por SignalR: el prerender puede haber enviado el HTML en la respuesta HTTP inicial.

TIEMPO: 16:00 – 21:00 Mostrar el código ANTES y avanzar para transformar el bloque en DESPUÉS. Ruta: /listas. Comparar Lento y Rápido. Después activar «Cargar bajo demanda» y desplazarse hasta el final de la lista. Items recibe una ICollection<Pedido>; no admite directamente un IReadOnlyList. Validación del 21/10 con una ventana de 1600×1000: 5.000 filas en Lento y 27 en Rápido. Con ItemsProvider se solicitaron 27 pedidos con skip=0&top=27. Al llegar al pedido 5000 seguía habiendo unas decenas de filas en el DOM. El número depende del tamaño de la ventana, la altura de las filas y las filas adicionales de margen que configura OverscanCount. El contador no incluye espaciadores ni filas de carga. El tiempo se mide desde la creación del componente hasta recibir del navegador un número de filas positivo y estable durante dos fotogramas. Incluye carga de datos, renderizado y comunicación. No es el tiempo de CPU del renderizado, ni el tiempo exacto que tarda el navegador en dibujar la interfaz, ni el tiempo total de navegación. Comparar sobre todo el número de filas; no prometer un porcentaje de mejora.

TIEMPO: 21:00 – 21:45 La variante bajo demanda no carga los 5.000 pedidos en el componente. La API simulada sí conserva todos sus datos en el servidor. No estamos demostrando una consulta paginada a una base de datos ni reduciendo esa memoria. ItemsProvider recibe StartIndex, Count y CancellationToken. Hay que pasar el token a la API para cancelar las solicitudes de filas que ya no se necesitan. La demo usa filas de 38 px y un contenedor de 520 px con desplazamiento vertical. También se puede virtualizar usando el desplazamiento de toda la página. SpacerElement="tr" permite usar espaciadores válidos dentro de tbody. Ya existía antes de .NET 9. Las filas que no están en el DOM no aparecen en la búsqueda del navegador ni al imprimir. Dejar estos detalles para las preguntas si no hace falta explicarlos.
